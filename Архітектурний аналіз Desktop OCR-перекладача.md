# Архітектурний аналіз Desktop OCR-перекладача

**Статус:** рекомендації перед початком розробки прототипу  
**Автор:** Manus AI  
**Дата:** 12 вересня 2026 року

## 1. Підсумковий висновок

Для першого прототипу рекомендовано **C# / .NET 8 / WPF** із модульною архітектурою та ізоляцією OCR і перекладу за інтерфейсами. Такий вибір відповідає Windows-орієнтованому сценарію: глобальна гаряча клавіша, прозоре overlay-вікно, багатомоніторне позиціювання та робота з Win32 API.

Найважливіше архітектурне рішення стосується OCR. API `Windows.Media.Ocr` підтримується для desktop-застосунків із **package identity**, тобто застосунок має бути встановлений і запущений як MSIX-пакет [1]. Тому вимогу «self-contained single-exe» не слід вважати основним способом дистрибуції, якщо Windows OCR є пріоритетним рушієм. Практична схема така:

1. **Основний Windows-варіант:** WPF-застосунок, упакований у MSIX, із `Windows.Media.Ocr`.
2. **Fallback / portable-варіант:** Tesseract із локальними мовними даними.
3. **Переклад:** окремий `ITranslationProvider`, перша реалізація — DeepL через HTTPS.

MVP має охоплювати один повний стабільний сценарій: хоткей → виділення → захоплення в пам’ять → OCR → переклад → редаговане floating-вікно. Історію, text-to-speech, Google Translate та складний редактор хоткеїв краще відкласти до стабілізації основного потоку.

## 2. Рекомендована структура

```text
/OcrTranslator

    CaptureCoordinator.cs

  /Models
    AppConfig.cs
    CaptureRegion.cs
    OcrResult.cs
    TranslationRequest.cs
    TranslationResult.cs
  /UI
    RegionSelectorWindow.xaml(.cs)
    ResultOverlayWindow.xaml(.cs)
    SettingsWindow.xaml(.cs)
    TrayIconManager.cs
  /Infrastructure
    Win32Interop.cs
    DpiService.cs
    Logging.cs
  App.xaml(.cs)
```

`CaptureCoordinator` має бути оркестратором сценарію, але не містити Win32- або UI-логіку. Він запускає окремі асинхронні етапи та передає вікну стан `Selecting`, `Recognizing`, `Translating`, `Ready` або `Error`. Це спрощує тестування та запобігає блокуванню UI-потоку.

### Потік даних

```text
Global hotkey
    -> RegionSelectorWindow
    -> CaptureRegion
    -> in-memory bitmap
    -> IOcrProvider
    -> recognized text
    -> ITranslationProvider
    -> ResultOverlayWindow
```

У пам’яті потрібно передавати не лише прямокутник, а й координатну систему, DPI та монітор. Це запобігає помилкам, коли виділення починається на одному дисплеї або масштабується на дисплеї з іншим коефіцієнтом.

## 3. Критичні ризики та рішення

| Ризик | Наслідок | Рекомендоване рішення | Пріоритет |
|---|---|---|---|
| `Windows.Media.Ocr` потребує package identity | Portable EXE не зможе надійно використовувати основний OCR API | Обрати MSIX для основної збірки; додати Tesseract fallback | Критичний |
| Різний DPI на кількох моніторах | Неправильна область захоплення, зміщене floating-вікно, розмитий UI | Увімкнути Per-Monitor V2 DPI awareness і тестувати mixed-DPI конфігурації [2] | Критичний |
| Конфлікт глобального хоткею | Застосунок не реагує або перехоплює небажану комбінацію | Перевіряти результат `RegisterHotKey`, показувати зрозумілу помилку, викликати `UnregisterHotKey` під час завершення [3] | Високий |
| Відсутній мовний пакет OCR | Порожній або низькоякісний результат для української чи російської | На старті перевіряти доступні OCR-мови та показувати інструкцію з інсталяції мовного пакета; мати Tesseract fallback [4] | Високий |
| Передавання скриншота зовнішньому API | Ризик витоку конфіденційної інформації | За замовчуванням залишати зображення локальним; до DeepL надсилати лише розпізнаний текст | Критичний |
| Порожній або шумний OCR-результат | Непотрібний API-запит і незрозумілий UI | Не перекладати порожній текст; показувати стан «Текст не розпізнано» та кнопку повторного OCR | Середній |
| Помилки мережі, rate limit або quota | Зависання або втрата результату | Тайм-аут, скасування через `CancellationToken`, exponential backoff для 429/5xx; не повторювати запит при вичерпаній квоті 456 [5] | Високий |
| API-ключ у JSON | Компрометація ключа через читання файлу | Шифрувати секрет через DPAPI `ProtectedData` зі scope `CurrentUser`; не записувати ключ у логи [6] | Критичний |
| Втрата фокусу floating-вікном | Переривання роботи користувача | `ShowActivated=false`, обережне використання Topmost, режим Pin для блокування автозакриття | Середній |

## 4. Рекомендації щодо OCR

`IOcrProvider` слід визначити так, щоб UI не знав, який рушій використовується:

```csharp
public interface IOcrProvider
{
    Task<OcrResult> RecognizeAsync(
        ReadOnlyMemory<byte> image,
        string language,
        CancellationToken cancellationToken);
}
```

У прототипі краще використовувати PNG-байти в пам’яті або `SoftwareBitmap`, а не тимчасові файли. Для Windows OCR потрібно окремо перевірити доступність мов на конкретній машині. Підтримка української, англійської та російської не повинна вважатися гарантованою лише на підставі коду: вона залежить від установлених мовних компонентів Windows [4].

Tesseract як fallback збільшує розмір дистрибутива та потребує комплекту `traineddata`, але дає контрольовану поведінку в portable-режимі. Інтерфейс провайдера має повертати також використану мову, confidence, час виконання та структурований список рядків, навіть якщо MVP відображає лише суцільний текст.

## 5. Рекомендації щодо перекладу

DeepL слід викликати тільки після локальної перевірки, що OCR повернув непорожній текст. API підтримує автоматичне визначення source language, якщо `source_lang` не передано, а цільову мову потрібно задавати явно [5]. У провайдері варто передбачити:

- `HttpClient` через dependency injection;
- тайм-аут і скасування запиту;
- перевірку максимальної довжини тексту та розбиття великих результатів;
- обробку HTTP 400, 429, 456 і 5xx окремими повідомленнями;
- логування `X-Trace-ID` без логування тексту або API-ключа;
- збереження останньої мовної пари локально.

Для редагованого OCR-тексту потрібен debounce приблизно 500 мс і захист від гонок: старий переклад не повинен перезаписати результат новішого запиту. Для цього слід застосувати лічильник версій запиту або скасування попереднього `CancellationToken`.

## 6. Безпека та приватність

Знімок екрана за замовчуванням не повинен записуватися на диск і не повинен потрапляти в історію без явного перемикача. Водночас користувач має бачити коротке пояснення, що для хмарного перекладу розпізнаний текст надсилається провайдеру.

DPAPI підходить для локального зберігання API-ключа: .NET дозволяє шифрувати дані в межах поточного облікового запису або всього комп’ютера [6]. Для персонального desktop-застосунку рекомендовано `DataProtectionScope.CurrentUser`, випадкова entropy та обмежені права на файл конфігурації. DPAPI не захищає ключ від шкідливого коду, який виконується від імені того самого користувача, тому це не заміна операційній безпеці.

## 8. План реалізації та перевірки

Перший етап — створити WPF-проєкт, підключити tray icon і реалізувати `RegisterHotKey`. Результат етапу: застосунок запускається в tray і відкриває selector за хоткеєм.

Другий етап — реалізувати selector і захоплення області. До інтеграції OCR потрібно перевірити скасування, нульову область, межі монітора, кілька моніторів і збереження правильних фізичних піксельних координат.

Третій етап — підключити Windows OCR у MSIX-збірці та додати перевірку доступних мов. Паралельно можна створити контракт і тестовий mock-провайдер, щоб UI розроблявся незалежно від мовних пакетів.

Четвертий етап — підключити DeepL, захистити API-ключ DPAPI та реалізувати retry-політику. Мережеві тести мають охоплювати відсутній ключ, тайм-аут, неправильну мову, 429, 456 та відсутність інтернету.

П’ятий етап — зібрати ResultOverlayWindow і виконати end-to-end перевірку. Критерієм готовності MVP є стабільне завершення сценарію менш ніж за 1–2 секунди для невеликої області за умови доступного OCR і мережі; цей показник слід вимірювати, а не гарантувати наперед.

## 9. Рішення, які потрібно зафіксувати до кодування

Рекомендовано зафіксувати такі значення за замовчуванням: **Ctrl+Shift+T**, автоматичне визначення мови джерела, українська як цільова мова, Windows OCR у MSIX-збірці, Tesseract як fallback, opacity 92%, темна тема або системна тема, відсутність збереження скриншотів.

Також потрібно прийняти продуктове рішення щодо приватності: чи дозволяти користувачу вмикати хмарний переклад для чутливих фрагментів. Технічно це можна обмежити індикатором «текст буде надіслано до DeepL» і явним перемикачем, але це має бути частиною UX, а не лише документації.
